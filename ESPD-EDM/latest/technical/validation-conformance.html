Validation and Conformance

ESPD Validation Steps

Depending on the type of application (ESPD Request or ESPD Response), different types of validations are executed:

Figure 1. ESPD Validation Process

ESPD Request Validation

  1. XSD Validation against QualificationApplicationRequest-2.4.xsd

  2. Code list validations (common for both Request and Response):

    1. Validation of the code list values: 01-ESPD-codelist-values.cva

    2. Validation of the identification of the code list: 01-ESPD-Common-CL-Attributes.sch

  3. Business rules related to the cardinality of the schema: 02-ESPD-req-cardinality-br.sch

  4. Business rules used to validate the criteria data structure:

    1. Validations common for Request and Response: 03-ESPD-common-criterion-br.sch

    2. Validations specific for Request: 03-ESPD-req-criterion-br.sch

  5. Other business rules:

    1. Common validations (schemeAgencyID for identifiers): 04-ESPD-common-other-br.sch

    2. Specific business rules for Request: 04-ESPD-req-other-br.sch

    3. Business rules related to the procurer: 05-ESPD-req-procurer-br.sch

    4. Specific business rules: 05-ESPD-req-specific-br.sch

ESPD Response Validation

  1. XSD Validation against QualificationApplicationResponse-2.4.xsd

  2. Code list validations (common for both Request and Response):

    1. Validation of the code list values: 01-ESPD-codelist-values.cva

    2. Validation of the identification of the code list: 01-ESPD-Common-CL-Attributes.sch

  3. Business rules related to the cardinality of the schema: 02-ESPD-resp-cardinality-br.sch

  4. Business rules used to validate the criteria data structure:

    1. Validations common for Request and Response: 03-ESPD-common-criterion-br.sch

    2. Validations specific for Response: 03-ESPD-resp-criterion-br.sch

  5. Other business rules:

    1. Common validations: 04-ESPD-common-other-br.sch

    2. Specific business rules for Response: 04-ESPD-resp-other-br.sch

    3. Business rules related to the economic operator: 05-ESPD-resp-eo-br.sch

    4. Response-specific business rules: 05-ESPD-resp-specific-br.sch

    5. Pre-qualification system rules: 05-ESPD-resp-qualification-br.sch

    6. Role-dependent business rules: 05-ESPD-resp-role-br.sch

UUID Criterion Validation

Each criterion is defined in e-Certis and has a Universally Unique Identifier (UUID) supplied by e-Certis:

  1. These UUIDs are mandatory and are maintained by the Publications Office.

  2. The criterion UUIDs can be found in the espd-edm.json file.

The UUIDs defined in the ESPDRequest or ESPDResponse are validated for the following elements:

Element XSD Path

Criterion

cac:TenderingCriterion/cbc:ID

Property Group

cac:TenderingCriterionPropertyGroup/cbc:ID

Property

cac:TenderingCriterionProperty/cbc:ID

Tendering Criterion Validation

The validation of each criterion (cac:TenderingCriterion element) checks:

  1. cbc:ID, cbc:CriterionTypeCode, cbc:Name and cbc:Description are mandatory;

  2. cbc:ID values match with the ones supplied by e-Certis;

  3. cac:TenderingCriterionPropertyGroup structure matches the expected QUESTION_GROUP or REQUIREMENT_GROUP.

Tendering Criterion Property Group and Subgroup

The same validations are executed for the first level group of properties and sub-groups of properties:

  1. The cbc:ID and cbc:PropertyGroupTypeCode are mandatory;

  2. cac:SubsidiaryTenderingCriterionPropertyGroup matches with QUESTION_SUBGROUP or REQUIREMENT_SUBGROUP;

  3. cac:TenderingCriterionProperty structure matches with QUESTION or REQUIREMENT or CAPTION.

Tendering Criterion Property

The validation of cac:TenderingCriterionProperty checks:

  1. cbc:TypeCode and cbc:ValueDataTypeCode are mandatory elements;

  2. cbc:ID and cbc:Description elements are mandatory (values not validated);

  3. If cbc:TypeCode value is "CAPTION", cbc:ValueDataTypeCode value must be "NONE".

XML Path Like ID

Starting with ESPD v4.0.0, UUIDs for all sub-elements are replaced by XML Path Like IDs in the data structure, except for the top-level Exclusion Grounds and Selection Criteria elements. For further details, see How Criteria Work. The XML Path Like ID is built programmatically.

Code List Validation (CVA)

Business rules related to code lists validate values and their mandatory attributes. This uses an extra step before the Schematron process: Genericode (GC) files as input.

The process:

  1. Generation of Genericode (GC) files — found in the codelists folder.

  2. Design and implementation of the CVA file (Context and Value Association) — specifies the association between XML elements and code list files.

  3. Execution:

    1. Transformation of CVA files into SCH files.

    2. Transformation of SCH files into XSLT.

    3. Execution of the validations and generation of the final report.

Figure 2. Code list validation architecture

Testing with the Interoperability Testbed

The Interoperability Testbed allows developers and integrators to test the validity of their ESPD XML instances by uploading them and launching the validation online.

All the ESPD-EDM artefacts necessary to perform the validation are set up in the testbed — no local installation is required.
